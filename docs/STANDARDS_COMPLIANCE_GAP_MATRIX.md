## Evidence rules and status legend

* **FIXED / TESTED**: a previously failing deterministic test passed on this audit branch; this is **not** a release/Full User E2E PASS.
* **IMPLEMENTED / PARTIAL**: source code contains a relevant mechanism; protocol completeness and live enforcement are not necessarily proven.
* **GAP**: missing/incomplete behavior or a published profile narrower than the cited RFC.
* **DESIGN EXCEPTION**: deliberately stricter product behavior; assess compatibility and document rather than silently weaken it.
* **NOT VERIFIED**: no sufficient audit evidence collected; must not be reported as PASS.
* RFC MUST/SHOULD requirements are normative **for the corresponding supported protocol**. NIST/OWASP/IEC/SLSA guidance and certification are not interchangeable with RFC conformance.

**Source-of-truth correction:** The v2.4 Internet Access policy is the **SQLite** control-plane database `/var/lib/drlink/drlink.db`, not legacy `egress-control.json` (see `docs/CONTROLLED_EGRESS.md`, §3 and §27). The gateway's runtime logic uses `frp_egress_control.py` utilities alongside `drlink_control_plane.py`. Testing helpers alone must not be mistaken for live authoritative policy.

## Product-specific deviations and security non-goals

1. HTTP request bodies using chunked Transfer-Encoding are deliberately unsupported by the small v2.4 forward-proxy profile; rejection is safer than partial/ambiguous decoding but narrower than a general HTTP/1.1 implementation.
2. HTTPS CONNECT is bound to observable TLS SNI, with ECH denied in this profile. No application TLS termination or decryption is promised; encrypted/hidden endpoint identity is a documented compatibility restriction.
3. Source-IP/CIDR identity in agentless egress can conflate machines behind NAT. That is not the same as per-host or per-human authentication.
4. The primary v2.4 Internet Access policy accepts ASCII FQDN values; full Unicode IDNA2008/UTS46 capability should be separately designed, not assumed from Python stdlib's legacy codec.
5. The release currently remains subject to the existing CLI Feature/Full User E2E contract, two passes on identical HEAD, and owner release authorization.
