## Current owner decision — strategic Rust runtime migration (2026-11-27 KST)

Rust is the selected long-term implementation language for the bounded native
runtime scopes below, for memory/resource safety, concurrency, maintainability
and operational reliability. This owner decision supersedes the older
conditional-adoption, profiling-prerequisite, language-comparison and numeric
performance-screening language in this report and prior checkpoints. Earlier
measurements remain historical evidence only; no faster-than-Python result is
an implementation or adoption gate.

Implementation order:

1. **R1:** integrate the Rust Internet Access / TCP Egress relay runtime.
2. **R2:** integrate bounded MCP connection I/O, dispatch/wait/streaming and
   backpressure runtime.
3. **R3:** integrate bounded Linux/macOS Agent and Server executor process/I/O
   lifecycle helpers.

Python remains the only CLI/configuration, OAuth, AI Identity, AI Access/policy,
durable job/nonce/audit and database authority. FRP remains Go; Windows Agent
remains PowerShell. Keep the change bounded to these native runtime paths: no
parallel policy implementation, wholesale rewrite or unrelated expansion.
Existing service limits and acceptance contracts remain. Pinned dependencies,
provenance, supported-platform packaging, fail-closed behavior and a verified
safe rollback are required. Functional/security/platform constraints can block
only their affected component; record the evidence and continue independent
work. The committed R1 relay experiment is evidence and a starting point, not
product integration.

R4–R6 remain required: integrate, add normative functional/security coverage,
run affected regression, independent code/security audit and fix/retest,
execute eligible real E2E, load/soak/resource bounds, packaging and rollback,
update current specifications and EN/KO documentation, commit/push, and verify
exact-HEAD CI. No production deployment or release is authorized by this work.

### R2 — MCP I/O and dispatch

The candidate now includes a pinned Rust atomic admission counter and bounded
job-output window (1 MiB retention, 64 KiB cursor pages) behind the Python
adapter. Python retains request authentication, AI Access, durable jobs,
nonce/audit, cursor ownership and validation, dispatch, result waiting, and
HTTP/TLS framing and connection ownership. The handler now passes response
bodies through a Rust writer capped at 64 KiB per callback; Python's socket/TLS
writer supplies the actual I/O and backpressure, and short writes are retried.
The handler also passes the already length-checked request body through Rust
reads capped at 64 KiB per callback; Python still owns the HTTP/TLS stream,
JSON parsing and all request authority. Rust-selected request-body, dispatch,
cursor and response-write regressions passed on Linux. Socket accept/connection
lifecycle and native result-wait integration remain unfinished; packaging of
the native library is also open.
No Rust R2 candidate was built in the earlier historical measurements. Existing same-source 8-worker runs measured
30-call p95 of 333/371 ms and 18.8/21.6 ms Bridge CPU per command; a separate
later 30-container allocator workload measured p95 1137 ms and 7.606 CPU
seconds. These are different layers/workloads and cannot be compared directly.
The 30-call Python profile also included DB/registry/nonce and dispatch work,
with high sampling lag; a separate 10-round attempt hit the public 120
POST/60-second limiter (184 of 300 calls returned HTTP 429) and was not
repeated or bypassed. Current evidence does not isolate a socket-runtime
contribution from queue/SQLite/job state. These are historical observations,
not an R2 disposition or an implementation prerequisite. Implement the
bounded MCP runtime in the required sequence while keeping OAuth, AI Access,
durable job/nonce and audit state in Python.

### R3 — Agent / Server executor

The candidate integrates bounded Rust stdout/stderr pipe draining and bounded
capture for Python-spawned Linux/macOS Agent and Server executors. Python keeps
account selection, process creation, request input, timeout selection,
process-group termination, reaping, AI Access, jobs and audit authority. Linux

pipes; denial on those paths remains a hard error. Native installer packaging
and complete supported-platform qualification remain open. Current measurements do not isolate
Linux/macOS executor subprocess I/O, job cleanup or encoding cost, and the
available real managed-host path was not executor-ready. These are historical
observations, not an R3 disposition or implementation prerequisite. Implement
bounded Linux/macOS helpers while preserving OS account, path constraints and
signed claim/complete flow; Windows Agent remains PowerShell.
