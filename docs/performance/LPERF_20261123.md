## Current owner decision — strategic Rust runtime migration (2026-11-27 KST)

Rust is the selected long-term implementation language for the bounded native
runtime scopes below, for memory/resource safety, concurrency, maintainability
and operational reliability. This owner decision supersedes the older
conditional-adoption, profiling-prerequisite, language-comparison and numeric
performance-screening language in this report and prior checkpoints. Earlier
measurements remain historical evidence only; no faster-than-Python result is
an implementation or adoption gate.

Implementation order:

1. **R1:** integrate the Rust Internet Access / TCP Egress relay runtime.
2. **R2:** integrate bounded MCP connection I/O, dispatch/wait/streaming and
   backpressure runtime.
3. **R3:** integrate bounded Linux/macOS Agent and Server executor process/I/O
   lifecycle helpers.

Python remains the only CLI/configuration, OAuth, AI Identity, AI Access/policy,
durable job/nonce/audit and database authority. FRP remains Go; Windows Agent
remains PowerShell. Keep the change bounded to these native runtime paths: no
parallel policy implementation, wholesale rewrite or unrelated expansion.
Existing service limits and acceptance contracts remain. Pinned dependencies,
provenance, supported-platform packaging, fail-closed behavior and a verified
safe rollback are required. Functional/security/platform constraints can block
only their affected component; record the evidence and continue independent
work. The committed R1 relay experiment is evidence and a starting point, not
product integration.

R4–R6 remain required: integrate, add normative functional/security coverage,
run affected regression, independent code/security audit and fix/retest,
execute eligible real E2E, load/soak/resource bounds, packaging and rollback,
update current specifications and EN/KO documentation, commit/push, and verify
exact-HEAD CI. No production deployment or release is authorized by this work.

## Codex review P2 closures (2026-11-24)

Review of PR #304 exact HEAD f23b07c0 found two actionable P2 issues:

1. Process cgroup memory: reading a fixed cgroup mount root ignored a
   nested systemd unit memory ceiling. The corrected worker auto policy
   resolves /proc/self/cgroup and /proc/self/mountinfo membership,
   supports both cgroup v1 and v2, walks ancestor memory limits and
   fails closed to one worker when membership/mount facts are unknown.
   Regression coverage: direct child limit 1GiB, ancestor 2GiB,
   non-root v1 mounted subtree, invalid/missing cgroup. Eight local
   worker-selection tests PASS. No installed service tuned.
3. Effective cgroup CPU quota: process affinity alone can expose 10 cores
   while the unit's cgroup quota permits only one. Auto now reads cgroup v2
   cpu.max or v1 cpu.cfs_quota_us / cpu.cfs_period_us from the process
   membership (and every accessible ancestor), bounds affinity by the
   minimum quota and falls back to one worker on missing quota evidence.
   Tests include v2 child/parent quotas, inherited CPU quota, v1 non-root
   controller mount, invalid/missing parents and unlimited values; the
   opt-in auto default does not change installed service configuration.

2. CONNECT transport delivery: a successful sendall only queued bytes
   locally, not proof of receipt. The disposable origin now sends a
   unique acknowledgement only after the expected ClientHello plus
   application payload bytes have been read, and the client requires
   that exact receipt. Invalid TLS ClientHello reproduction reports
   origin received 0B, acknowledgements 0, failure rate 100%, and
   PERFORMANCE_BENCHMARK=FAIL. Five focused Egress regression tests
   PASS, including HTTP Forward and concurrent DENY/audit.

Original 6-vs-8 worker source-bound p95 comparisons are retained as
historical clean-source evidence (d89d0008); do not silently relabel
them as measurements on the reviewed-fix commit. Exact source and

## P2 review closure: true cgroup v2 root CPU quota

At PR #304 HEAD 93d0964, Codex identified a CPU auto-tuning error:
the true cgroup v2 hierarchy root legitimately has no cpu.max file.
The previous code interpreted that missing root interface as an unknown
ancestor quota, forcing one worker even with ten affinity CPUs and 8 GiB.

RED regression: reported 1 instead of expected 10 effective CPUs.
GREEN fix: tolerate FileNotFoundError only when cgroup v2 mount_root is
the true "/" and the current node is that mount root. Missing cpu.max on
non-root cgroups, including bind-mounted subtrees, still fails closed;
unreadable/malformed quotas still fail closed. The explicit worker
configuration and legacy default of one remain unchanged.

MCP server_exec launches tests as subprocesses inside the installed
drlink-mcp-bridge.service cgroup. Its systemd MemoryCurrent / MemoryPeak
therefore include those synthetic 100-Agent benchmark child processes,
not only the installed Bridge; it is invalid to infer Bridge process
memory leaks from those aggregate counters without process attribution.

## Fixed TCP listener backlog: bounded configuration applied before listen

On dev-drlink, candidate 8535160f, a source-local 50/100-way loopback
profile found that RelayServer sets request_queue_size=64 after
TCPServer.__init__ already called listen(). Activation actually used the
Python default backlog of 5. A regression intercepted server_activate
and failed with [5] != [64]. Moving the existing bounded value to the
class before activation preserves the session and per-source admission
limits; no production setting was changed.
